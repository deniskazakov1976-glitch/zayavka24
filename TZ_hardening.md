# ТЗ для ИИ-разработчика: доработка проекта «Заявка 24/7» (BotAvitoTelegram)

## 0. Контекст и правила работы

**Проект:** ИИ-менеджер продаж для локальных автобизнесов РФ. Каналы: Telegram (aiogram 3.14) и Авито Messenger API v3. Бэкенд: Python 3.12, FastAPI/Uvicorn, SQLite (`data/bot.db`), LLM через Polza.ai (OpenAI-совместимый API, `openai/gpt-4o-mini`). Профили компаний лежат в `companies/*.yaml`. Есть веб-дашборд (`app/dashboard.py`, `app/templates/dashboard.html`).

**Ключевые файлы:** `main.py`, `app/config.py`, `app/models.py`, `app/storage.py`, `app/llm.py`, `app/prompt_builder.py`, `app/avito.py`, `app/telegram_bot.py`, `app/server.py`, `app/dashboard.py`, `app/notifier.py`, `app/media_reply.py`, `tests/test_core.py`.

**Правила:**
- Зависимости: только бесплатные или самохостинг. Не добавлять платные SDK и зарубежные платёжные сервисы.
- Все тексты для пользователя: на русском, UTF-8.
- Не ломать существующее поведение: `.\.venv\Scripts\pytest.exe -v` сейчас даёт 16 passed и должен оставаться зелёным.
- На каждый пункт: код, автотесты (pytest, без реальных сетевых вызовов, внешние сервисы мокать), обновление `.env.example` и `README`/инструкции.
- Секреты не логировать и не коммитить.
- Работать пунктами в порядке из раздела «Порядок выполнения». После каждого пункта запускать полный набор тестов.
- В конце дать отчёт: что сделано, какие файлы изменены, как проверить, что осталось.

## 1. Деплой на VPS (работа 24/7, домен, HTTPS, автозапуск)

**Проблема:** бот работает только пока включён ПК владельца. Временный туннель (pinggy/ngrok) меняет адрес, и вебхук Авито приходится регистрировать заново.

**Сделать:**
1. `Dockerfile` (python:3.12-slim, непривилегированный пользователь, `pip install --no-cache-dir -r requirements.txt`, `CMD ["python", "main.py"]`).
2. `docker-compose.yml`:
   - сервис `app` с `restart: unless-stopped`, томами `./data:/app/data` и `./companies:/app/companies`, `env_file: .env`, healthcheck на `/health`;
   - сервис `caddy` (Caddy 2) как reverse proxy с автоматическим HTTPS Let's Encrypt, домен из переменной `DOMAIN`;
   - порт приложения наружу не публиковать, только через Caddy.
3. `deploy/Caddyfile`:
   - `{$DOMAIN}` → проксирует **только** `/webhook/*` и `/health` на `app:8080`;
   - дашборд (`/`, `/api/*`) наружу **не отдавать** (доступ через SSH-туннель) либо закрыть basic-auth + IP-allowlist через переменные.
4. `deploy/bot.service`: альтернативный systemd-юнит без Docker (`Restart=always`, `EnvironmentFile`, запуск из venv).
5. `deploy/README_DEPLOY.md`: пошаговая инструкция для новичка:
   - покупка VPS (Ubuntu 22.04, 1 vCPU / 1 GB) у российского провайдера;
   - покупка домена и A-запись;
   - установка Docker, `git clone`, заполнение `.env`, `docker compose up -d`;
   - регистрация вебхука Авито **один раз** на `https://<домен>/webhook/avito/<секрет>`;
   - обновление (`git pull && docker compose up -d --build`), просмотр логов, перенос `data/` с ПК.
6. Скрипт `scripts/backup.sh` и cron-пример: см. п. 11.
7. В `app/config.py` добавить `PUBLIC_BASE_URL`. Дашборд, в поле Webhook URL, должен подставлять его автоматически вместо `currentHost`.
8. При старте, если `AVITO_ENABLED=true` и задан `PUBLIC_BASE_URL`, предлагать (по кнопке в дашборде) авто-регистрацию вебхука.

**Приёмка:** `docker compose up -d` на чистой машине поднимает бота, `https://<домен>/health` → 200, перезагрузка VPS не ломает работу, дашборд снаружи недоступен.

## 🔴 Критичные (К1–К6): чинить ДО первого клиента, выполнять первыми

### К1. Дашборд открыт наружу
**Проблема:** `DASHBOARD_PASSWORD` по умолчанию пустой, `WEBHOOK_HOST=0.0.0.0`. Если пробросить порт 8080 через pinggy/ngrok для Авито, весь дашборд (заявки с телефонами, `/api/avito/config`, `/api/gaps`) окажется в интернете. Файлы: `config.py`, `dashboard.py`.
**Сделать:**
1. Дашборд и вебхук разделить: дашборд слушает только `127.0.0.1` (отдельный порт, `DASHBOARD_PORT`, `DASHBOARD_HOST=127.0.0.1` по умолчанию), вебхук слушает на `WEBHOOK_HOST:WEBHOOK_PORT`. Через туннель или Caddy наружу отдаётся только вебхук.
2. Если дашборд включён и `DASHBOARD_PASSWORD` пуст, а `DASHBOARD_HOST` не loopback, приложение **отказывается стартовать** с понятной ошибкой. При loopback и пустом пароле только предупреждение в лог.
3. `start.bat` и `.env.example`: пароль генерируется при первом запуске, если пуст (и записывается в `.env`).
4. `/api/avito/config` и `/api/gaps` не отдают секреты (только `is_set`), всё за авторизацией (детали в п. 6).
**Тесты:** отказ старта при публичном хосте без пароля; `/api/*` на порту вебхука недоступен (404); секрет не возвращается.

### К2. Вебхук Авито без проверки подлинности
**Проблема:** `/webhook/avito` принимает любой POST. Файл `server.py`. Последствия: поддельные события, трата баланса Polza, ответы в чужие чаты.
**Сделать:**
1. Секрет в пути: `/webhook/avito/{secret}`, `AVITO_WEBHOOK_SECRET` (генерируется автоматически при первом запуске, минимум 32 символа, сравнение `secrets.compare_digest`). Старый путь без секрета возвращает 404. Дашборд при регистрации вебхука подставляет полный URL с секретом.
2. Если Авито передаёт подпись или заголовок, проверять их тоже (по документации API мессенджера); иначе опираться на секрет в URL.
3. Валидация: `chat_id` и `author_id` из события проверять через Avito API (`GET /messenger/v2/accounts/{user_id}/chats/{chat_id}`): чат принадлежит аккаунту. Лимит размера тела запроса (≤64 КБ), общий rate-limit по IP на вебхук.
4. Неверный секрет: 404 без деталей, запись в лог (без тела), счётчик попыток для алерта.
**Тесты:** верный секрет → 200; неверный/пустой → 404; чужой `chat_id` игнорируется; превышение размера → 413.

### К3. Вебхук отвечает после LLM, нет дедупликации и блокировок
**Проблема:** `avito.py handle_event` держит запрос, пока LLM думает; Авито ждёт пару секунд и повторяет доставку → двойные ответы. Два сообщения подряд в одном чате обрабатываются параллельно.
**Сделать:**
1. Вебхук мгновенно отвечает `200 {"ok": true}` и ставит событие в очередь (`asyncio.Queue` с воркерами, число воркеров `AVITO_WORKERS`, по умолчанию 4). Обработка идёт в фоне.
2. Дедупликация: таблица `processed_events(channel, message_id PRIMARY KEY, created_at)`; повторное событие с тем же `message_id` пропускается (INSERT OR IGNORE, проверка до постановки в очередь). Чистка записей старше 7 дней.
3. Блокировка на чат: `asyncio.Lock` на `(channel, chat_id)` (словарь с очисткой); сообщения одного чата обрабатываются строго по очереди. Если за время обработки пришло ещё сообщение клиента, перед ответом подтянуть всю историю (бот отвечает на сводный контекст, а не плодит два ответа). Рекомендуется «дебаунс» 2–3 секунды: накопить серию быстрых сообщений и ответить один раз.
4. Устойчивость очереди: при перезапуске необработанные события не теряются. Хранить статус события в `processed_events` (`received/processing/done/failed`) и при старте дообрабатывать `received/processing` младше 10 минут.
5. Те же блокировки и дедупликация для Telegram (по `update_id`/`message_id`).
**Тесты:** повторная доставка одного `message_id` даёт один ответ; два параллельных сообщения одного чата обрабатываются последовательно; вебхук отвечает быстрее 200 мс при медленном LLM (мок с задержкой); восстановление после «падения».

### К4. Эхо бота принимается за ответ владельца
**Проблема:** `_bot_sent_message_ids` хранится в памяти. После перезапуска пуст; если эхо пришло раньше, чем `send_message` вернул id, бот сам ставит чат на паузу на 24 часа. Баг тихий.
**Сделать:**
1. Хранить отправленные ботом сообщения в БД: таблица `bot_sent_messages(channel, chat_id, message_id, text_hash, created_at)`.
2. Устранить гонку: **до** отправки записывать «ожидаемое эхо» (`chat_id`, хэш текста, время, статус `pending`), после ответа API дописывать `message_id`. Эхо считается ботовым, если совпал `message_id` **или** (`chat_id` + хэш текста + окно ±30 секунд, `pending`).
3. Автопауза только для исходящих сообщений, которые не совпали ни по id, ни по хэшу. Дополнительно сверять `author_id == user_id` и тип сообщения (системные сообщения Авито не считать ответом владельца).
4. Журнал решений: каждое включение паузы пишется в лог/БД с причиной (`manual_owner_reply`, сообщение, время). В дашборде видно «чат на паузе, причина, до какого времени», кнопка «снять паузу». Алерт владельцу платформы, если пауз за час подозрительно много (> `PAUSE_ALERT_THRESHOLD`).
5. Очистка старых записей `bot_sent_messages` (старше 48 часов).
**Тесты:** эхо до возврата `send_message` не вызывает паузу; эхо после перезапуска (пустая память) не вызывает паузу; настоящий ответ владельца даёт паузу; хэш-совпадение вне окна даёт паузу.

### К5. Нет защиты от падения LLM
**Проблема:** вызов LLM в `llm.py` без `try/except`, таймаута и ретрая. Если Polza недоступна или баланс нулевой, клиент остаётся без ответа, лид пропадает.
**Сделать:**
1. Таймаут вызова (`LLM_TIMEOUT_SEC`, по умолчанию 25), до 2 ретраев с экспоненциальной паузой на сетевые ошибки, 429 и 5xx; **без** ретрая на 401/402/400.
2. Резервная модель (`LLM_FALLBACK_MODEL`, необязательно) и/или запасной провайдер (`LLM_FALLBACK_BASE_URL`, `LLM_FALLBACK_API_KEY`): переключение при ошибке основного.
3. Аварийный ответ клиенту, если LLM недоступна совсем: «Спасибо за обращение! Оставьте, пожалуйста, номер телефона, мастер свяжется с вами {media_reply_promise}». Если номер уже есть в сообщении клиента, извлечь его регулярным выражением (уже есть `extract_phone_fallback`) и сохранить лид **без LLM**, подтвердив получение.
4. Алерт владельцу платформы в Telegram (с антиспамом 1 раз в 30 минут на тип ошибки): таймаут, 401/402/429, нулевой баланс, переход на резерв.
5. Режим деградации: счётчик подряд идущих ошибок; после N ошибок бот переходит в упрощённый режим «собрать номер и передать мастеру» на M минут, затем пробует снова.
6. Все исключения в обработчиках Telegram и Авито перехватываются на верхнем уровне: клиент не остаётся без ответа, ошибка идёт в лог и алерт.
**Тесты (мок клиента OpenAI):** таймаут → ретрай → успех; 402 → без ретрая, аварийный ответ, алерт; падение основного → резервная модель; номер в сообщении при мёртвой LLM сохраняется как лид; антиспам алертов.
